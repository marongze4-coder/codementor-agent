## 文档说明

CodeMentor Agent 是一个面向程序设计课程的智能实训与评测平台。它把课程问答、编程作业评测、代码质量审查和项目答辩拆成四个职责不同的 Agent，再通过统一入口、数据库和业务状态把它们连接成一条完整学习链路。

这份文档不讲具体代码写法，而是回答三个问题：

1. 这个项目解决了什么问题，为什么要这样设计。
2. 系统内部如何运转，各项技术分别承担什么职责。
3. 面试时应该怎样用自己的语言把项目讲清楚，并应对后续追问。

这份报告特别强调数据来源与真实性。项目中的“真实”不是指模型说得像真的，而是指每个关键结论都能回答四个问题：原始数据是谁提供的、系统保存了什么标识、结论由什么过程产生、最后由谁负责确认。

> 最重要的表达口径：课程知识来自教师提供的资料，测试标准来自教师配置，待评代码来自学生实际上传，运行结果来自 Docker 的真实执行，模型评价只是辅助判断，正式成绩来自教师确认。当前仓库中的示例课程和 3 个测试用例属于演示数据，只能证明流程跑通，不能冒充真实学校数据或模型准确率。

阅读时不要急着背名词。先理解一条最核心的业务流程：

> 学生学习知识并提交代码，系统运行测试和分析质量，教师确认成绩，学生再根据真实提交进行项目答辩。

如果这条主线能讲清楚，再把 RAG、LangGraph、Docker 沙箱、Human in the Loop 等技术放回对应环节，整个项目就容易理解了。

# 1 项目背景与业务目标

## 1.1 课程实训中的实际问题

程序设计课程和普通理论课不同。学生只有真正编写、运行和调试代码，才能确认自己是否理解知识。但是在实际教学中，教师很难持续完成以下工作：

- 学生遇到语法、算法和工程问题时，需要及时答疑，但教师无法随时在线。
- 一次作业可能有几十甚至上百份代码，逐份运行、检查边界条件和统计成绩耗时很长。
- 程序能运行不代表代码质量好。命名、模块划分、异常处理、复杂度和安全问题都需要额外审查。
- 课程项目完成后，教师还要通过答辩判断学生是否真正理解代码，而不是只提交了一份能运行的结果。
- 如果完全依赖大模型评分，可能出现判断不稳定、解释缺少依据或错误分数直接发布的问题。

因此，这个项目没有把目标定成一个简单的聊天机器人，而是构建一套覆盖学习、练习、评测、改进和答辩的实训平台。

## 1.2 项目目标

平台希望完成以下目标：

| 目标 | 具体含义 |
|---|---|
| 提高答疑效率 | 使用课程知识库回答高频编程问题，并保留引用依据 |
| 自动验证代码 | 使用教师配置的测试用例运行学生代码，检查输入输出和边界条件 |
| 评价工程质量 | 从六个维度分析代码，而不只判断最终输出是否正确 |
| 保留教师终审 | 自动评测只提供建议分，最终成绩由教师确认后发布 |
| 验证真实理解 | 答辩 Agent 根据学生自己的作业和问题连续追问 |
| 支持降级运行 | 没有大模型密钥时，规则分析、代码测试和人工确认仍然可以使用 |

## 1.3 项目定位

这个项目适合定位为一个课程实训原型，而不是已经承载大规模学校生产流量的平台。它具备完整业务闭环和工程基础，可以用于课程设计、毕业项目、实习面试和后续工程扩展。

面试时可以这样界定项目：

> 我基于一个教育多 Agent 工程完成了程序设计课程场景的业务重构，重点实现了代码沙箱评测、六维代码审查、教师成绩确认和基于真实提交的项目答辩，并保留了原有的 RAG 问答与统一 Agent 架构。

这个表述比直接说“我从零做了一个生产平台”更可信，也更经得住追问。

# 2 平台角色与完整业务闭环

## 2.1 三类用户角色

平台包含学生、教师和管理员三类角色。

| 角色 | 主要操作 | 权限边界 |
|---|---|---|
| 学生 | 课程问答、提交作业、查看自己的评测、上传代码审查、参加答辩 | 只能查看自己的提交、审查和答辩记录 |
| 教师 | 新建课程、发布作业、配置测试用例、查看待确认提交、发布成绩 | 可以管理当前租户下的课程和评测数据 |
| 管理员 | 具备教师管理能力，并负责系统级配置 | 适合后续扩展用户和租户管理 |

## 2.2 一条完整学习链路

平台的核心不是四个独立页面，而是下面这条数据连续流动的链路：

> 教师创建课程和作业  →  配置公开与隐藏测试用例  →  学生提交 Python 源文件  →  系统并行运行功能测试和质量分析  →  生成自动评测结果  →  教师确认并发布成绩  →  学生根据问题修改代码  →  关联提交记录开始项目答辩  →  生成答辩报告

这条链路里有四个关键点：

第一，系统保存的不是一段临时对话，而是课程、作业、测试用例、代码提交、测试结果、审查报告和答辩会话等结构化数据。

第二，每一步的结果都能成为下一步的上下文。例如，答辩 Agent 会读取作业要求、自动得分、薄弱点和代码审查问题，避免提出与学生项目无关的通用问题。

第三，自动评分与最终成绩分离。系统可以提高教师效率，但不会绕过教师直接发布正式成绩。

第四，数据来源需要能够追溯。课程规则由教师创建，代码记录上传学生和文件摘要，测试结果关联具体用例，答辩关联具体提交；模型生成内容不能覆盖这些原始事实。

## 2.3 为什么业务闭环比单个功能更有价值

如果系统只有代码审查，它只能告诉学生“哪里写得不好”；如果只有自动测试，它只能告诉学生“结果对不对”；如果只有答辩，它又缺少真实代码作为依据。把三者连接后，平台可以同时观察功能正确性、工程质量和学生理解程度。

面试时可以把这个特点概括为：

> 项目的价值不在于四个 Agent 数量多，而在于同一份学生代码会经过自动测试、质量审查、教师确认和答辩验证，前序结果能够给后序环节提供证据。

# 3 系统整体架构

## 3.1 六层架构

整个系统可以从上到下分成六层。

| 层级 | 主要技术 | 职责 |
|---|---|---|
| 前端交互层 | Vue 3、TypeScript、Element Plus | 提供学生端和教师端页面，展示流式回答、评测结果和答辩记录 |
| API 接入层 | FastAPI、Pydantic、JWT | 接收请求、校验参数、验证用户身份、控制角色权限、返回结果 |
| 统一编排层 | 意图路由、统一响应、SSE | 判断用户需求，引导到合适功能，并统一流式事件格式 |
| Agent 工作流层 | LangGraph、LangChain | 用状态、节点和边表达问答、评测、审查和答辩流程 |
| 公共能力层 | LLM Factory、本地模型、重试、日志、Docker 沙箱 | 向不同 Agent 提供统一模型调用、检索、容错和代码执行能力 |
| 数据存储层 | PostgreSQL、Milvus | 保存业务记录、用户数据、评测结果和课程知识向量 |

可以把一次请求想象成如下过程：

> 浏览器发起请求  →  FastAPI 验证 JWT  →  业务接口组装初始状态  →  LangGraph 执行节点  →  节点调用数据库 本地模型 大模型或沙箱  →  结构化结果保存到 PostgreSQL  →  前端轮询或通过 SSE 展示结果

## 3.2 各项技术为什么存在

### FastAPI

FastAPI 负责系统入口。它适合这个项目的原因是原生支持异步请求、参数校验、依赖注入和自动接口文档。代码审查和作业评测耗时较长，接口可以先返回任务编号，再由后台继续执行，避免浏览器一直等待。

### LangGraph

LangGraph 负责描述业务流程。普通函数调用适合简单直线处理，但这里存在条件分支、并行任务、多轮状态和结束条件。LangGraph 可以把每一步拆成节点，让状态在节点间传递，并通过普通边或条件边决定下一步。

### PostgreSQL

PostgreSQL 保存强结构化业务数据，例如用户、课程、作业、提交记录和成绩。项目大量使用 JSONB 字段保存维度评分、问题列表和答辩报告，这样既保留关系数据库的一致性，也能灵活存储 Agent 的结构化输出。

### Milvus

Milvus 用于保存课程资料的向量表示。学生提问后，系统可以根据语义和关键词从大量课程分块中找出相关内容，而不是把整门课一次性放进大模型上下文。

### 本地模型

BGE M3、BGE Reranker 和 MiniLM 在后端进程内加载。它们分别承担向量生成、候选文档精排和高频问题分类。把这些高频轻量任务交给本地模型，可以减少大模型调用费用和延迟。

### DeepSeek

DeepSeek 负责需要语言理解和综合判断的任务，例如基于知识生成回答、深入评价代码和生成答辩反馈。所有模型调用经过统一工厂创建，便于统一配置模型名称、温度、超时和结构化输出。

### Docker

Docker 用于隔离运行学生代码。直接在后端主机执行未知代码会带来命令执行、文件访问和资源耗尽风险，因此代码必须放入受限制的独立容器运行。

# 4 为什么拆成四个 Agent

## 4.1 Agent 与普通大模型调用的区别

一次普通大模型调用只有输入和输出。Agent 则包含输入感知、状态保存、路径判断、工具调用和结果持久化。它并不等于“让模型自由决定一切”，而是把模型放进一个受控业务流程中。

LangGraph 中四个最重要的概念可以这样理解：

| 概念 | 通俗解释 | 在本项目中的例子 |
|---|---|---|
| State | 一张不断补充内容的任务单 | 保存学生编号、源文件、测试结果、当前答辩阶段等 |
| Node | 一名只负责一件事的工作人员 | 加载作业、运行测试、分析质量、生成问题 |
| Edge | 工作人员之间的流转规则 | 测试和审查结束后进入汇总节点 |
| Checkpoint 或持久化 | 保存任务当前进度 | 多轮问答记忆、答辩消息和阶段记录 |

## 4.2 四类业务的流程形状不同

| Agent | 核心任务 | 主要流程范式 |
|---|---|---|
| 程序设计问答 | 从课程资料中找到依据并回答 | RAG 检索 分支路由 多轮记忆 |
| 编程作业评测 | 同时判断程序输出和代码质量 | 并行工作流 自动汇总 人工终审 |
| 代码质量审查 | 从多个独立维度检查同一份代码 | 多维并行评审 结构化汇总 |
| 项目答辩 | 根据阶段连续提问并生成报告 | 状态机 多轮会话 条件结束 |

如果把所有逻辑塞进一个全能 Agent，会出现三个问题：提示词越来越长、状态字段互相干扰、测试和维护困难。按业务边界拆分后，每个 Agent 只处理一种流程，并共享认证、数据库、模型和日志等公共能力。

## 4.3 为什么选择受控工作流

教育评测对可解释性和稳定性要求较高。项目没有让大模型自行决定是否发布成绩，也没有让模型直接执行任意工具。关键流程由代码确定，大模型只在需要语义理解的节点参与。

这个设计的核心思想是：

> 确定的事情交给规则，不确定的事情交给模型，高风险的事情交给人工确认。

# 5 程序设计问答 Agent

## 5.1 为什么需要 RAG

通用大模型知道公开的编程知识，但不知道课程讲义、教师要求和项目约定。如果学生询问“本课程为什么这样设计”或“作业中的入口函数要求是什么”，模型可能给出通用答案，甚至编造不存在的规定。

RAG 的处理方式是先检索课程知识，再让模型根据检索结果回答。这样可以覆盖私有内容，也能把来源返回给学生。

## 5.2 RAG 的两个阶段

### 离线知识库构建

课程资料先经过读取、分块、向量化和入库四个步骤。

1. 读取由教师或课程负责人确认的 PDF、Word 或 Markdown 等课程文件。
2. 根据段落和长度切分成适合检索的知识块。
3. 使用 BGE M3 同时生成稠密向量和稀疏向量。
4. 将向量、正文、课程编号、文档编号、来源名称和分块位置保存到 Milvus。

这一步可以理解为先把教材整理成一个能够按语义搜索的书架。

### 在线问题查询

学生提出问题后，系统执行以下流程：

> 问题分类  →  根据问题类型选择直接检索 HyDE 或多查询改写  →  稠密与稀疏混合召回  →  Reranker 精排  →  判断置信度  →  基于知识库回答或走兜底路径  →  保存会话记忆

## 5.3 问题分类

不是所有问题都需要知识库。例如“Python 列表和元组有什么区别”属于公开通用知识；“本课程第三次作业的输入格式是什么”属于课程专有问题。

系统使用本地 MiniLM 模型完成高频分类。当模型对“通用问题”的置信度达到 0.85 时，可以直接交给大模型回答；否则保守地进入 RAG 流程。这个阈值偏高的原因是宁可多检索一次，也不要漏掉课程专有问题。

对于不同形态的课程问题，系统还支持两种查询增强：

- 问题表达模糊时，使用 HyDE 先生成一段可能的答案描述，再用这段描述检索。
- 问题范围较宽时，拆成多个更具体的查询分别召回，再合并结果。

## 5.4 混合检索

项目同时使用稠密检索和稀疏检索。

- 稠密检索理解语义，能识别不同表达中相近的意思。
- 稀疏检索关注关键词，适合查找准确的类名、API 名称和错误信息。

两路结果在 Milvus 中通过 WeightedRanker 融合。当前权重为稠密 0.7、稀疏 0.3，因为课程问题通常以语义理解为主，同时保留精确术语匹配能力。

## 5.5 为什么还需要 Reranker

混合检索返回的是“向量上比较相似”的候选文档，不一定真正能够回答问题。因此系统先召回约 10 个候选，再使用 BGE Reranker 对“问题和文档”成对评分，选出最相关的 3 条内容。

Reranker 的最高相关性分数还作为置信度依据。当前阈值为 0.75：高于阈值时优先基于课程知识回答；低于阈值时进入直接回答、联网补充或待补充知识等兜底路径。

## 5.6 多轮记忆

学生经常会继续追问“为什么”“能再举个例子吗”。如果系统每轮只看到当前问题，就无法理解代词和上下文。问答 Agent 使用会话编号隔离不同学生和不同对话，并在历史过长时通过滑动窗口和摘要压缩控制上下文长度。

这里要区分两件事：

- 完整历史用于保存和追踪。
- 送给大模型的内容需要裁剪或摘要，否则 Token 会不断增加。

## 5.7 问答数据如何追溯

RAG 的真实性首先取决于入库文档本身是否可信，而不是取决于向量模型有多强。项目保存 `document_id`、`source_name`、`course_id`、`chunk_index` 和 `tenant_id` 等元数据。PDF 来源可以标注到文件名和页码，Markdown 来源可以标注到标题层级。回答时同时返回来源名称，便于学生或教师回到原文核对。

这里必须区分三个概念：

- “检索到相关内容”只代表文本相关，不代表内容一定正确。
- “回答带有来源”代表可以追溯，不代表模型的每句话都已被来源支持。
- “课程规则有效”最终取决于教师是否确认入库文档是当前版本的正式资料。

因此，生产化时还应增加文档上传人、版本号、生效时间、文件摘要和审核状态，并做回答与引用的一致性校验。当前项目已经具备来源元数据、租户过滤、置信度路由和低置信度待补充队列，但不能把这些能力夸大成完整的数据治理平台。

## 5.8 面试时怎样概括问答 Agent

> 问答 Agent 不是直接把问题交给大模型，而是先用本地模型判断是否需要课程知识。需要检索时，BGE M3 同时生成稠密和稀疏表示，在 Milvus 中按 7 比 3 融合召回，再用 Reranker 从候选中选出最相关的 3 条。最后根据 0.75 的置信度决定基于知识库回答还是走兜底路径。知识块保留文档、页码或标题、课程和租户等来源信息，回答会返回引用；但课程资料是否权威仍要由教师审核。

# 6 编程作业评测 Agent

## 6.1 输入与输出

教师先配置课程、作业要求、入口文件、评分权重和测试用例。学生选择作业并上传 Python 源文件后，系统返回提交编号，在后台完成评测。

最终评测结果包含：

- 功能测试得分。
- 代码质量得分。
- 各测试用例是否通过及运行耗时。
- 代码质量维度分数和问题列表。
- 薄弱点和综合反馈。
- 自动建议分、教师分和最终发布分。

## 6.2 为什么功能测试和质量审查并行

功能测试只依赖作业测试用例和源文件，质量审查只依赖源代码内容，两者没有前后依赖。因此系统在加载完作业信息后，同时启动两条路径：

> 路径一  在 Docker 沙箱中并行运行测试用例  
> 路径二  对代码结构和工程质量进行静态分析  
> 两条路径完成后进入统一汇总

如果串行执行，用户等待时间等于两部分耗时相加；并行后，总耗时更接近其中较慢的一条。

## 6.3 功能测试得分

每个测试用例包含标准输入、预期输出、超时时间、权重和是否对学生隐藏。系统在独立容器中运行代码，比较标准输出与预期输出。

功能分按照通过用例的权重计算：

> 功能得分 = 已通过测试权重之和 ÷ 全部测试权重之和 × 100

隐藏测试用例可以减少学生针对公开样例硬编码答案的情况。学生只能看到隐藏用例是否通过，不会看到完整标准输入输出。

## 6.4 代码质量得分

质量分析复用六维代码审查能力。作业自动评分中，功能正确性主要由真实测试负责，所以质量分重点统计算法、可读性、可维护性、健壮性和安全性。

默认评分权重为：

- 功能测试占 60%。
- 代码质量占 40%。

教师创建作业时可以调整这一比例。自动建议分的计算方式为：

> 自动建议分 = 功能得分 × 功能权重 + 质量得分 × 质量权重

当沙箱不可用时，系统不会把功能分当成已验证结果，而是只保留质量部分，并强制要求教师复核。

## 6.5 教师确认机制

无论自动评分是多少，提交完成后都会进入待确认状态。教师可以查看自动得分、测试结果、问题列表和薄弱点，再填写最终成绩和评语。

系统会重点标记以下情况：

- 沙箱未运行成功。
- 存在未通过的测试用例。
- 自动建议分低于 70 分。

这种做法体现了 Human in the Loop 思想：AI 和规则负责减少重复工作，教师保留最终判断权。

## 6.6 后台任务设计

代码运行和质量分析不是瞬时操作。如果上传接口一直等待，用户可能遇到超时，也会长期占用连接。因此接口先返回 202 Accepted 和提交编号，前端根据编号轮询状态。

状态会经历：

> evaluating 评测中  →  pending review 等待教师确认  →  published 已发布

如果执行过程中出现无法恢复的异常，状态会变为 failed，并保存错误信息供排查。

## 6.7 面试时怎样概括作业评测

> 学生上传代码后，接口先返回任务编号，后台同时运行 Docker 功能测试和代码质量分析。功能分按测试用例权重计算，质量分来自工程维度分析，默认按 60 比 40 合成建议分。结果不会直接发布，而是进入教师确认队列，教师查看测试证据后再给最终成绩。

# 7 代码质量审查 Agent

## 7.1 为什么不能只看程序是否运行成功

两个程序可能输出相同结果，但工程质量完全不同。课程训练除了“做对”，还要让学生理解复杂度、模块设计、异常处理和安全习惯。

代码审查 Agent 支持 Python、Java、JavaScript、TypeScript、C、C++ 和 Go 文件。Python 可以进行更深入的抽象语法树分析；其他语言当前主要完成通用规则和结构检查。

## 7.2 六个审查维度

| 维度 | 权重 | 关注内容 |
|---|---:|---|
| 功能正确性 | 25% | 语法、明显逻辑错误、边界条件和结果正确性 |
| 算法与复杂度 | 20% | 算法选择、时间复杂度、空间复杂度和重复计算 |
| 可读性与规范 | 15% | 命名、格式、注释、函数职责和表达方式 |
| 模块化与可维护性 | 15% | 模块划分、重复逻辑、耦合、可测试性和扩展性 |
| 异常处理与健壮性 | 15% | 输入校验、异常处理、空值和极端情况 |
| 安全性 | 10% | 危险函数、命令执行、路径、输入和敏感信息 |

综合分是各维度得分与权重的加权结果，并转换为 A 到 E 等级。

## 7.3 本地静态分析

没有大模型密钥时，系统仍然可以执行本地分析。以 Python 为例，系统会先解析抽象语法树，提取类、函数、导入项和入口结构，并检查：

- Python 语法错误。
- 过长代码行。
- 函数过长或控制流嵌套过深。
- 大多数函数缺少说明。
- 裸 except 吞掉全部异常。
- 可变对象作为默认参数。
- eval、exec、os.system 和 shell 等危险执行方式。

每个问题都包含所属维度、严重程度、行号或证据，以及可执行的修改建议。

## 7.4 大模型深度审查

配置 DeepSeek 密钥后，系统会针对六个维度发起相互独立的结构化评审。六个任务并行执行，总耗时接近最慢的一次调用，而不是六次调用相加。

大模型结果不会完全替代本地规则。当前维度分会结合两部分结果：大模型分析占 75%，本地规则基线占 25%。本地明确检测到的风险也会合并进最终问题列表。

这样设计有两个目的：

1. 大模型擅长理解代码意图和给出解释。
2. 规则适合发现确定性强的问题，结果更稳定。

如果某一个维度的大模型调用失败，只降级该维度，不影响其他维度和整份报告。

## 7.5 问题合并与排序

多个维度可能发现相同问题。系统会根据问题标题和行号去重，并按 critical、high、medium、low 的顺序排列。最终报告提供：

- 六维度分数。
- 综合得分和等级。
- 优势项。
- 优先修改问题。
- 下一步修改建议。

## 7.6 面试时怎样概括代码审查

> 我没有让大模型直接给一个总分，而是把代码质量拆成六个维度。Python 代码先通过 AST 和确定性规则做基线检查，配置模型后再并行完成六维语义评审。最后按权重汇总，并对问题按行号和严重程度去重排序。没有密钥时本地分析仍然能工作，避免整个功能完全依赖外部模型。

# 8 项目答辩 Agent

## 8.1 为什么答辩必须关联真实代码

通用答辩机器人通常只会问“请介绍项目”“遇到了什么困难”等固定问题，无法判断学生是否理解自己提交的程序。

本项目创建答辩会话时，必须关联一次作业提交或已经完成的代码审查。答辩 Agent 会读取：

- 作业标题和要求。
- 自动评测得分。
- 未通过测试和薄弱点。
- 代码审查分数与问题。
- 前几轮答辩消息。

因此问题可以围绕真实证据展开，例如“你的异常处理维度较弱，如果输入为空会发生什么”，而不是随机提问。

## 8.2 五阶段状态机

答辩过程被拆成五个阶段：

| 阶段 | 目标 | 典型问题 |
|---|---|---|
| 项目概述 | 确认学生理解任务目标 | 这个程序解决什么问题，输入输出是什么 |
| 设计思路 | 检查数据结构和模块设计 | 为什么选择这种结构，函数如何分工 |
| 调试分析 | 检查定位问题的能力 | 某个失败用例可能是什么原因，如何复现 |
| 优化改进 | 检查复杂度和工程意识 | 如果数据量增大，哪里需要优化 |
| 总结 | 形成复盘和下一步计划 | 如果再做一次，你会先改哪部分 |

系统显式保存当前阶段和轮次，而不是让大模型每轮从全部对话中猜测“现在问到哪里”。当前实现每两轮推进一个阶段，最多 10 轮。学生输入“结束答辩”等关键词时，可以提前进入报告阶段。

## 8.3 模型可用与不可用时的区别

配置大模型密钥后，每轮回答会得到结构化评价、证据和下一道问题，结束时生成包括架构、编码、调试和表达能力的综合报告。

密钥为空时，系统使用本地固定问题完成流程，但不会伪造 AI 得分。答辩结束后状态标记为等待教师或模型评价。这种降级比随意给一个默认分更诚实。

## 8.4 状态持久化

每轮学生回答和系统问题都会保存到 PostgreSQL，答辩会话还记录阶段、轮次、状态、报告和结束时间。即使浏览器刷新，前端也能重新加载会话记录。

## 8.5 面试时怎样概括答辩 Agent

> 答辩 Agent 是一个五阶段状态机。它不靠大模型猜当前流程，而是由确定的阶段字段控制概述、设计、调试、优化和总结。每次答辩必须关联真实作业或代码审查，所以问题可以利用自动得分和薄弱点进行追问。达到 10 轮或收到结束关键词后进入报告节点，整个会话持续写入数据库。

# 9 四个 Agent 如何形成协作闭环

## 9.1 统一入口

统一助手先处理问候、感谢等简单话术，这类请求直接使用本地模板，不消耗大模型 Token。对于业务请求，系统通过关键词规则和大模型路由识别意图：

- 编程概念和课程问题进入程序设计问答。
- 提交作业和自动测试进入编程实训。
- 代码规范和质量问题进入代码审查。
- 项目讲解和连续追问进入项目答辩。
- 同时涉及多个环节时，前端展示完整实训步骤计划。

在当前版本中，统一助手主要负责识别与引导。作业、审查和答辩仍在各自页面完成，这是因为它们需要文件上传、作业选择和会话操作，不适合全部塞进一个聊天输入框。

## 9.2 数据协作比形式上的 Agent 调用更重要

多 Agent 协作并不一定意味着一个大模型自动调用另一个大模型。本项目更重要的协作方式是结构化数据传递：

> 作业评测产生得分和薄弱点  →  代码审查产生问题和建议  →  答辩读取这些结果并追问  →  教师结合多类证据确认成绩

这种方式比自由的动态 Agent 协商更可控，也更容易审计。

## 9.3 一个具体例子

以示例作业“成绩统计器”为例：

1. 教师要求读取一组成绩，输出平均分、最高分和最低分。
2. 学生提交程序后，系统运行基础数据、单个成绩和边界成绩三个用例。
3. 功能测试全部通过，但代码质量分析仍会检查模块划分、异常处理和输入边界。
4. 自动建议分进入教师确认页面，教师查看证据后发布最终分数。
5. 学生可以基于该提交开始答辩，解释为什么这样拆分函数、如何处理空输入、数据量增大时复杂度如何变化。

同一个作业从“能运行”逐步走到“写得好”和“讲得明白”，这就是平台闭环。

# 10 数据来源、真实性与权限控制

## 10.1 先说清楚当前数据是什么

项目中的数据分为“用户输入的原始数据”“系统运行产生的事实”“模型或规则推导的判断”和“教师确认的正式结果”四类。四类数据的可信程度不同，展示和讲解时不能混为一谈。

| 数据类型 | 直接来源 | 系统保留的追溯信息 | 应该怎样理解真实性 |
|---|---|---|---|
| 课程知识 | 教师或课程负责人提供的 PDF、Word、Markdown | 文档编号、来源名称、页码或标题、课程编号、租户编号、分块编号 | 来源可追溯；内容是否权威仍由教师审核 |
| 外部网络补充 | 检索服务返回的公开网页 | 网页 URL | 只能作为补充信息并明确标注，不能覆盖教师课程规则 |
| 课程和作业要求 | 教师或管理员创建 | 创建者、课程、租户、语言、评分权重 | 属于教师配置的教学规则，不是模型生成的规则 |
| 测试用例与标准输出 | 教师配置 | 所属作业、输入、预期输出、权重、超时、是否隐藏 | 是功能评测标准；覆盖多少场景决定证明力度 |
| 学生源代码 | 登录学生实际上传的文件 | 学生编号、作业编号、原文件名、保存路径、SHA-256、提交时间 | 可以证明系统处理的是该次上传文件，但不能仅凭摘要证明代码一定由本人原创 |
| 沙箱运行结果 | Docker 容器真实执行 | 关联提交和用例、是否通过、退出码、耗时、错误信息 | 在给定环境和给定用例下可复核，不等于程序对所有输入都正确 |
| 本地静态分析 | Python AST 和确定性规则 | 问题类型、严重程度、行号、规则说明 | 对语法结构和命中规则的事实性较强，但规则覆盖范围有限 |
| 大模型审查与答辩评价 | 源代码、测试结果、学生回答等上下文经过模型推断 | 维度分、问题、理由、建议、会话消息 | 属于概率性建议，可能有偏差，不能当作客观事实 |
| 最终成绩 | 教师查看证据后输入并发布 | 教师分、最终分、审核人、审核时间、发布时间 | 是平台内正式结果，责任主体是教师 |

当前仓库中的 `PY101` 示例课程、“成绩统计器”作业和 3 个测试用例由初始化脚本生成，是为了验证系统流程的演示数据，不是来自真实学校教务系统的生产数据。报告中的 100、82、93、95 等分数也都是这组演示数据的运行结果。它们证明“系统能按设计执行”，不能证明“模型评分准确率达到某个水平”。

## 10.2 四层真实性模型

为了讲清数据可信度，可以把平台中的数据分成四层：

1. 原始记录层：教师资料、作业要求、测试用例、学生上传代码和学生答辩原话。系统的职责是绑定身份、时间和业务编号，尽量保留原貌。
2. 可复现事实层：代码哈希、沙箱退出码、运行耗时和用例通过状态。这些结果由确定性程序产生，在相同镜像、依赖和输入下可以重新执行核对。
3. 智能判断层：代码质量分、薄弱点、答辩评价和自然语言总结。这些由规则或大模型推导，应显示依据和不确定性，不能覆盖原始数据。
4. 人工决策层：教师最终成绩和评语。教师查看前三层证据后确认，系统记录审核人和时间。

这四层的关系可以概括为：

> 原始数据保留  →  确定性程序产生证据  →  Agent 基于证据提出建议  →  教师作出正式决定

最关键的设计原则是“原始数据和派生结论分开保存”。例如，教师修改最终分数不会改掉自动建议分，模型生成答辩总结也不会覆盖学生原回答。这样出现争议时可以回看当时的输入、运行结果和审核过程。

## 10.3 各环节如何降低数据失真

### 课程问答

- 课程专有问题优先检索教师资料，不让模型凭通用知识猜课程规定。
- 知识块保留来源名称、文档编号、课程、租户和位置，回答返回来源。
- 重排最高分低于 0.75 时走兜底路径，并可将问题写入待补充队列，而不是强行生成“课程答案”。
- 如果使用网络补充，来源应以 URL 单独展示，并与课程正式资料区分。
- 租户和课程过滤防止检索到其他学校或其他课程的资料。

### 作业评测

- 测试输入和标准输出由教师配置，不由大模型临时编造。
- 学生提交时计算 SHA-256 文件摘要，用于识别同一次上传内容是否发生变化。
- 每个结果关联具体提交和具体测试用例，同时记录退出码、耗时和错误。
- 自动分和教师最终分分字段保存，状态经过 `evaluating`、`pending_review`、`published`，避免未审核结果被当作正式成绩。

### 代码审查

- AST 和规则发现的问题保留明确类型和行号，属于可直接核对的证据。
- 大模型负责上下文理解与改进建议，但结果被定位为“建议”，不伪装成编译器事实。
- 无密钥时只返回本地规则结果，不虚构模型已经完成了深度评价。

### 项目答辩

- 创建答辩必须关联一条属于当前学生的作业提交或代码审查记录。
- 问题上下文来自作业要求、测试结果、薄弱点和历史回答，而不是凭空生成一个虚构项目。
- 每轮消息、阶段和轮次持续写入数据库；无密钥模式不伪造答辩得分，而是等待教师或模型后续评价。

## 10.4 九张核心业务表形成证据链

| 数据对象 | 保存内容 | 与其他对象的关系 |
|---|---|---|
| 课程 | 名称、编号、语言、创建者 | 包含多个作业和选课记录 |
| 课程选课 | 课程和学生关系 | 防止重复选课 |
| 作业 | 要求、语言、入口文件、评分权重 | 属于一门课程 |
| 测试用例 | 输入、预期输出、权重、隐藏状态 | 属于一个作业 |
| 代码提交 | 学生、源文件、文件摘要、状态、自动分和最终分 | 属于一个作业 |
| 测试结果 | 通过状态、退出码、耗时和错误 | 属于一次提交和一个测试用例 |
| 作业评审 | 功能分、质量分、问题、教师意见 | 与一次提交一一对应 |
| 代码审查 | 六维得分、问题、总结和状态 | 属于一个学生，可关联作业提交 |
| 答辩会话 | 阶段、轮次、消息、报告和得分 | 可关联课程、提交或代码审查 |

关系数据库中的外键和业务编号把数据连成证据链。看到一个最终分数时，可以向前找到教师审核记录、自动建议分、具体测试结果、学生提交以及教师配置的测试标准；看到一条答辩结论时，也可以向前找到使用了哪次提交和哪些问题。

## 10.5 为什么部分结果使用 JSONB

测试用例和成绩适合固定字段，但不同代码可能产生数量不同的问题，不同答辩报告也可能包含不同长度的优势和建议。如果为每个问题都设计大量固定列，结构会变得复杂。

因此系统将维度评分、问题列表、薄弱点和答辩报告保存为 JSONB，同时把用户编号、课程编号、状态、分数和时间等需要查询的字段保留为普通关系列。JSONB 提供结构灵活性，但其中仍应保留问题维度、行号、严重程度和理由等可解释字段，不能只保存一段无法追踪的模型长文本。

## 10.6 认证、权限与数据归属

用户登录后获得 JWT，令牌中包含用户编号、角色和租户编号。每个受保护接口都会校验令牌。

权限控制主要包括：

- 学生只能读取自己的提交、审查和答辩。
- 教师或管理员才能创建课程、作业和测试用例。
- 教师或管理员才能确认并发布成绩。
- 数据查询同时包含租户编号，避免不同机构之间的数据混用。

JWT 解决的是请求身份，数据库条件解决的是数据归属。只检查“是否登录”但不检查记录所有者，仍然可能出现越权访问。

## 10.7 当前真实性边界

现有机制能做到来源追踪、文件完整性摘要、运行证据保存、人工终审和租户隔离，但还不能解决所有真实性问题：

- SHA-256 能证明两份文件内容是否一致，不能证明作者身份，也不能替代查重和抄袭检测。
- 三个示例用例只能覆盖演示场景，不能证明程序在全部输入下正确。
- 来源名称能帮助核对文档，当前仍缺少完整的文档审批、版本发布和失效机制。
- 数据库记录可以追踪流程，但尚未实现不可篡改审计日志、操作签名和数据备份恢复演练。
- 代码质量和答辩评价缺少教师标注评测集，因此不能宣称达到确定的准确率。

面试时主动说明这些边界，反而能体现对数据真实性的理解。真实性不是一句“数据是真的”，而是一套来源、身份、完整性、过程证据、人工责任和可复核机制。

# 11 Docker 代码沙箱设计

## 11.1 为什么不能直接运行学生代码

学生提交的代码属于不可信输入。即使不是恶意代码，也可能出现死循环、无限递归、占满内存或启动大量进程。如果直接在 FastAPI 进程所在主机运行，可能影响整个服务。

## 11.2 当前沙箱限制

每个测试用例在一次性 Docker 容器中运行，主要限制如下：

| 限制 | 作用 |
|---|---|
| 禁用网络 | 防止代码访问外部服务或下载内容 |
| 只读根文件系统 | 防止修改容器系统文件 |
| 源码只读挂载 | 学生程序只能读取自己的提交文件 |
| 256 MB 内存限制 | 防止异常内存占用 |
| 0.5 CPU 限制 | 控制单次任务计算资源 |
| 最多 64 个进程 | 降低进程炸弹风险 |
| 删除全部 Linux capabilities | 减少容器特权 |
| no new privileges | 防止执行过程获得更高权限 |
| 最长 5 秒 | 终止死循环和超时程序 |
| 运行结束自动删除 | 避免残留容器长期占用资源 |

## 11.3 沙箱结果

沙箱会返回退出码、标准输出、标准错误、运行时间和错误类型，并单独记录输出是否通过。常见错误包括：

- timeout 运行超时。
- runtime error 程序异常退出。
- source missing 源文件不存在。
- sandbox unavailable Docker 或镜像不可用。
- 程序正常结束但输出与预期不同时，`passed` 为 false；它属于测试未通过，不一定对应一个运行错误类型。

## 11.4 当前沙箱的边界

Docker 隔离适合本地课程原型，但不能直接等同于公网生产级沙箱。生产环境还需要考虑专用执行节点、任务队列、镜像白名单、系统调用过滤、磁盘配额、并发配额、审计和容器逃逸防护。

面试时不要说“Docker 可以保证绝对安全”。更准确的说法是：

> 当前实现通过网络、权限、文件系统和资源限制降低风险，满足本地课程原型；如果面向公网，需要把代码执行拆成独立沙箱服务并继续加强隔离。

# 12 可靠性 性能与成本控制

## 12.1 无密钥降级

项目当前允许 DeepSeek 密钥为空。不同功能采用不同降级方式：

| 功能 | 有密钥 | 无密钥 |
|---|---|---|
| 程序设计问答 | 生成 RAG 或通用回答 | 检索基础仍在，但最终自然语言生成需要模型 |
| 代码审查 | 本地规则加六维大模型评审 | 使用 AST 和规则生成本地报告 |
| 作业评测 | 沙箱测试加本地质量分析，可继续扩展模型评价 | 沙箱测试和静态质量分析照常运行 |
| 项目答辩 | 动态评价回答并生成结构化报告 | 使用固定阶段问题，不伪造分数，等待教师评价 |

降级设计的原则不是所有功能都输出相同质量，而是外部模型不可用时系统仍能保存任务、提供确定性结果，并明确标记哪些判断尚未完成。

## 12.2 并行执行

项目有两处典型并行：

- 六个代码评审维度相互独立，可以并行调用模型。
- 作业的功能测试和质量分析没有依赖，可以同时执行。

并行只能用于无数据依赖的任务。如果后一项必须使用前一项的结果，就应该保持串行。

## 12.3 后台任务和轮询

代码审查和作业评测先返回任务编号，耗时操作在后台执行。前端轮询任务状态，直到完成或失败。这种方式提高了请求稳定性，也能给用户持续反馈。

当前后台任务仍运行在 FastAPI 进程内。服务突然重启时，正在执行的任务可能中断。生产环境应使用 Celery、RQ 或其他消息队列，把任务状态和重试交给独立 Worker。

## 12.4 本地模型预热和复用

后端启动时加载嵌入、重排和分类模型，避免第一个用户请求临时加载模型。统一模型工厂还会复用大模型客户端，减少重复创建连接和配置不一致。

## 12.5 Token 成本控制

系统通过以下方式减少不必要的大模型调用：

- 问候和感谢由本地规则直接回复。
- 高频问题分类使用 MiniLM，而不是每次调用大模型。
- 课程资料先检索并精排，只把少量最相关内容送给模型。
- 代码审查传递结构摘要和有限长度源码，避免无限增加上下文。
- 对话历史过长时进行裁剪和摘要。

## 12.6 日志与健康检查

系统记录应用启动、路由判断、Agent 节点、沙箱执行和失败信息，并提供健康检查接口。当前已经具备定位问题的基础，但还没有完整接入 Langfuse、Prometheus 或链路追踪平台。

# 14 项目中的关键难点与设计取舍

## 14.1 难点一 正确运行未知代码

最直接的做法是在后端执行学生上传的 Python 文件，但风险很高。项目最终选择一次性 Docker 容器，并同时限制网络、文件系统、内存、CPU、进程数和时间。

这个难点体现的是安全意识，而不是会不会调用 Python 解释器。

## 14.2 难点二 分数必须有证据

如果直接让大模型给代码打分，结果不稳定，也难以解释。项目将功能正确性与工程质量分开：功能分来自可重复运行的测试用例，质量分来自规则和模型分析，最终结果还需要教师确认。

这种设计降低了单一模型判断对正式成绩的影响。

## 14.3 难点三 模型不可用时系统不能瘫痪

大模型密钥可能没有配置，也可能因为限流、余额或网络不可用。项目为不同业务设计了不同降级：代码审查使用本地规则，作业评测依靠沙箱，答辩使用固定问题但不伪造评分。

降级策略必须符合业务语义，不能所有错误都统一返回一个“默认 60 分”。

## 14.4 难点四 多轮答辩的流程控制

如果完全由大模型决定下一问，模型可能重复问题、忘记阶段或提前结束。项目使用状态机显式记录阶段和轮次，大模型只负责评价和生成当前阶段的问题。

这个取舍让流程更可预测，也更容易测试。

## 14.5 难点五 RAG 检索质量

只使用向量相似度可能漏掉 API 名称和错误码，只使用关键词又不理解语义。因此项目采用稠密与稀疏混合召回，再通过 Reranker 精排，并用置信度决定是否相信知识库结果。

## 14.6 难点六 自动化和人工判断的边界

系统可以自动运行测试，但不能仅凭少量测试用例证明程序完全正确；模型可以提供代码建议，但不能代替教师发布正式成绩。项目把自动结果定义为建议和证据，把最终决定留给教师。

## 14.7 面试回答困难时的通用结构

遇到“为什么这样设计”的问题，可以按以下顺序回答：

1. 先说业务风险或技术问题。
2. 再说项目采用的方案。
3. 说明这个方案解决了什么。
4. 主动补充当前边界和生产优化方向。

例如：

> 学生代码属于不可信输入，直接运行可能影响主机，所以我使用受限 Docker 容器执行，并设置网络、资源和超时限制。这个方案能满足本地课程原型，但公网生产环境还要拆成独立沙箱集群并增加系统调用和并发控制。

# 15 当前边界与后续优化

## 15.1 当前边界

1. 作业自动运行目前只支持 Python，其他语言只能进行通用代码审查。
2. Docker 沙箱适合本地原型，还不是面向公网的高安全执行平台。
3. 后台任务运行在 Web 进程内，没有持久化任务队列。
4. QA 的最终回答和答辩深度评价仍需要大模型密钥。
5. QA 的部分会话检查点使用进程内存，服务重启后不能完整恢复。
6. 当前统一入口主要做意图识别和页面引导，没有让多个 Agent 自由动态规划。
7. 尚未建设教师标注的代码评分集、路由评测集和 RAG 标准问答集。
8. 尚未完成高并发压力测试、全链路追踪和线上指标看板。

## 15.2 优先优化顺序

### 第一阶段 完成可稳定演示版本

- 配置 DeepSeek 密钥并验证全部大模型路径。
- 导入真实程序设计课程资料，建立 RAG 知识库。
- 增加更多作业和边界测试用例。
- 为核心业务补充自动化接口测试。

### 第二阶段 提高工程可靠性

- 使用消息队列和独立 Worker 执行评测任务。
- 使用 PostgreSQL Checkpointer 持久化 Agent 状态。
- 将代码执行拆成独立沙箱服务。
- 增加任务幂等、失败重试、超时回收和并发配额。

### 第三阶段 提高教学效果

- 建立教师标准分和代码问题标注集。
- 统计学生跨作业的薄弱知识点。
- 根据错误类型自动推荐学习资料和下一道练习。
- 增加代码相似度和抄袭检测。

### 第四阶段 提高可观测性

- 接入 Langfuse 或 LangSmith 记录模型调用链路。
- 统计路由准确率、检索命中率、降级率和 P95 延迟。
- 对提示词和模型版本执行离线回归及在线对比。

## 15.3 面试中如何诚实说明边界

> 当前项目已经跑通课程、作业、沙箱测试、质量审查、教师确认和答辩闭环，但定位仍是本地实训原型。生产化最重要的改动是把后台任务和代码执行拆成独立服务，增加持久化队列、强隔离、可观测性和评测集。我会把这些作为下一阶段，而不会把当前 Docker 配置描述成绝对安全的生产沙箱。

# 16 面试项目介绍模板

## 16.1 一句话版本

> 我做了一个程序设计课程智能实训与评测平台，把课程 RAG 问答、Docker 代码测试、六维代码审查、教师确认和基于真实提交的项目答辩连接成完整教学闭环。

## 16.2 三十秒版本

> 这个项目主要解决程序设计课程中答疑不及时、代码作业批改量大，以及学生只会提交代码但讲不清思路的问题。系统分成四个 Agent：问答 Agent 基于教师课程资料回答并返回来源；作业 Agent 用教师测试用例在 Docker 中真实运行学生上传代码；代码审查 Agent 从六个维度提出有证据的建议；答辩 Agent 关联学生实际提交进行五阶段追问。模型结果只作辅助，自动成绩不会直接发布，教师确认后才形成最终分数。

## 16.3 两分钟版本

> 我把项目定位为程序设计课程的实训和评测平台。教师先创建课程、作业和公开或隐藏测试用例，学生提交 Python 文件后，FastAPI 先返回任务编号，后台同时做两件事：一条路径在受限 Docker 容器里运行测试，另一条路径做代码质量分析。功能分和质量分默认按 60 比 40 合成建议分，之后进入教师确认队列。
>
> 除了作业评测，平台还有独立代码审查功能。它把质量拆成正确性、复杂度、规范、可维护性、健壮性和安全性六个维度。Python 会先做 AST 和规则检查，配置大模型后再并行完成六维语义审查。这样没有密钥时仍能给出本地报告，有密钥后可以得到更深入的解释。
>
> 学生完成作业后，可以关联这次提交开始项目答辩。答辩不是普通聊天，而是概述、设计、调试、优化和总结五阶段状态机。它会读取作业要求、测试结果和薄弱点，围绕真实代码追问。系统还保留原有 RAG 问答，使用 BGE M3 的稠密和稀疏混合检索、Reranker 精排以及置信度路由。整个项目用 PostgreSQL 保存业务状态，用 Milvus 保存课程向量，并通过 JWT 和角色权限隔离学生与教师操作。
>
> 在数据真实性上，我把信息分成原始记录、可复现事实、智能判断和人工决定四层：课程资料和测试标准由教师提供，源代码由登录学生上传并记录 SHA-256，测试结果来自具体容器和具体用例，模型评分只是建议，最终成绩记录审核教师和时间。当前的“成绩统计器”和 3 个用例是演示数据，我只用它证明链路跑通，不把它说成真实学校数据或准确率结论。

## 16.4 五分钟版本

五分钟介绍建议按“问题、架构、主链路、难点、边界”展开。

### 第一部分 项目问题

> 程序设计课程的难点不只是回答知识问题，还要运行学生代码、检查工程质量并验证学生是否真正理解。教师逐份处理成本高，而单纯使用大模型又缺少确定性和正式评分所需的责任边界。

### 第二部分 整体架构

> 系统前端使用 Vue 3，后端使用 FastAPI。业务流程用 LangGraph 表达，PostgreSQL 保存课程、提交、评审和答辩，Milvus 保存课程知识向量。本地的 BGE M3、Reranker 和 MiniLM 分别负责嵌入、精排和问题分类，DeepSeek 负责语言生成和深入评价。

### 第三部分 主业务链路

> 教师配置作业和测试用例，学生提交代码后，Docker 功能测试和代码质量分析并行执行。系统生成建议分和问题证据，教师确认后发布成绩。学生可以再基于这次提交进行答辩，答辩 Agent 读取薄弱点并按五阶段继续追问。

### 第四部分 三个重点难点

> 第一个难点是不可信代码执行。我没有在后端直接运行文件，而是放进一次性 Docker 容器，禁网、只读、限制 256 MB 内存、0.5 CPU、64 个进程和 5 秒时间。第二个难点是模型结果不稳定，所以功能正确性由真实测试提供证据，代码分析同时保留本地规则，最终成绩由教师确认。第三个难点是数据真实性，我让知识、测试、代码、运行结果和审核记录都有明确来源，并把原始数据与模型派生结论分开保存。

### 第五部分 验证和边界

> 我完成了一次端到端验证：示例作业 3 个测试全部通过，功能分 100、质量分 82、建议分 93，教师最终发布 95；无密钥代码审查也能定位 4 个问题。当前仍是本地原型，下一步会把后台任务迁移到持久化队列，并把 Docker 执行拆成独立沙箱服务，同时建设 RAG 和评分评测集。

## 16.5 用 STAR 结构讲个人工作

如果面试官问“你在项目里具体做了什么”，可以按实际参与范围回答：

- Situation：原项目是通用教育多 Agent 案例，业务集中在简历、试卷和模拟面试，不适合我的程序设计课程项目方向。
- Task：我需要保留 Agent 工程基础，将业务改造成可以提交代码、自动测试、质量审查、教师确认和项目答辩的平台。
- Action：我重新设计课程领域数据，增加安全沙箱，拆分作业评测和代码审查流程，重构答辩上下文，并补齐学生端和教师端页面及端到端验证。
- Result：项目成功创建 9 张新业务表，跑通 3 个测试用例、自动评分、教师发布和答辩流程，前后端构建通过，无密钥情况下核心确定性功能仍可运行。

只保留自己真正理解并能继续解释的 Action。不要把课件中没有亲自验证的功能说成已经完成的大规模生产能力。

# 17 高频面试问题与回答

## 17.1 为什么要用多 Agent 而不是一个大 Prompt

答：四个业务的流程形状不同。问答需要 RAG 分支和记忆，作业评测需要并行测试和人工确认，代码审查需要六维并行评价，答辩需要阶段状态机。如果全部放进一个 Prompt，状态和工具会互相干扰，也难以单独测试。拆分后每个 Agent 高内聚，并共享认证、模型和数据库等基础设施。

## 17.2 为什么使用 LangGraph

答：项目不只是固定的问答链。它包含检索后的置信度分支、两个评测任务并行、答辩阶段推进和结束条件。LangGraph 可以显式定义 State、Node 和 Edge，让流程控制由程序决定，而不是隐藏在提示词中。

## 17.3 LangGraph 和 LangChain 有什么区别

答：LangChain 更适合封装模型、提示词和工具调用，LangGraph更适合表达有状态、带分支或循环的工作流。本项目用 LangChain 提供模型与消息抽象，用 LangGraph组织完整业务流程，两者是配合关系。

## 17.4 Agent 之间如何协作

答：当前最重要的协作是结构化数据传递。作业评测把得分和薄弱点写入数据库，代码审查保存问题列表，答辩创建时读取这些结果作为上下文。统一助手还负责识别意图和展示实训步骤。生产环境可以继续扩展动态编排，但教育评分优先选择可控流程。

## 17.5 为什么 RAG 要混合检索

答：稠密向量擅长理解语义，但可能漏掉精确类名和错误码；稀疏向量擅长关键词匹配，但不理解同义表达。两路按 0.7 和 0.3 融合，可以兼顾语义和术语。

## 17.6 为什么召回后还要重排

答：向量相似只说明文本在表示空间中接近，不一定真正能回答问题。系统先快速召回 10 个候选，再让 CrossEncoder 同时阅读问题和候选文档，选出最相关的 3 个。这样兼顾检索速度和精度。

## 17.7 如何减少 RAG 幻觉

答：先提高检索质量，再根据精排置信度决定是否使用知识库答案。最终响应返回来源，低置信度时走兜底而不是强行引用。进一步还可以增加答案与来源一致性校验和低置信度拒答。

## 17.8 为什么问题分类用本地模型

答：每个问题都需要分类，这是高频路径。MiniLM 体积小、延迟低且不产生调用费用。跨 Agent 的复杂意图路由频率较低，才使用规则和大模型结合。不同频率和复杂度的任务采用不同模型更合理。

## 17.9 如何处理长对话

答：完整历史可以持久化，但不能全部发送给模型。系统采用滑动窗口保留近期对话，并把早期内容压缩成摘要。这样既保留上下文，又控制 Token。生产环境还可以把重要事实写入长期语义记忆。

## 17.10 如何保证代码执行安全

答：不在 Web 主机直接执行学生代码，而是在一次性 Docker 容器中运行，禁用网络，根文件系统只读，源码只读挂载，限制内存、CPU、进程和超时，并删除 Linux capabilities。这个方案降低了风险，但公网环境还需要独立沙箱服务和更强系统调用隔离。

## 17.11 遇到死循环怎么办

答：每个用例都有超时时间，系统使用异步超时控制终止容器进程。容器还受到 CPU 和内存限制，避免单个提交长期占用资源。生产环境应由任务队列和执行节点负责超时回收。

## 17.12 自动分数可靠吗

答：自动分是建议分，不直接作为正式成绩。功能分来自测试用例证据，质量分来自规则和模型分析，最后由教师确认。测试用例覆盖不足和模型判断偏差都可能影响自动分，所以保留 Human in the Loop。

## 17.13 为什么功能分和质量分分开

答：测试可以证明已覆盖输入下的输出是否正确，但不能评价命名、模块化和安全；质量分析可以发现工程问题，但不能替代实际运行。两类证据互补，默认按 60 比 40 合成。

## 17.14 为什么代码审查使用六个维度

答：直接给总分缺乏解释。拆成正确性、复杂度、规范、可维护性、健壮性和安全性后，每个分数都对应明确关注点，学生知道下一步改什么，教师也能检查评分依据。

## 17.15 大模型和规则冲突怎么办

答：确定性强的问题优先保留规则证据，例如语法错误、裸 except 和危险函数。大模型负责理解上下文和提供改进解释，分数按一定比例融合。生产中还可以为高危规则设置硬性扣分或直接进入人工复核。

## 17.16 为什么答辩要用状态机

答：普通多轮聊天容易重复问题或忘记进度。状态机显式保存当前阶段和轮次，代码负责推进和结束，大模型只负责当前阶段的评价与下一问。职责分离后流程可预测，也方便单元测试。

## 17.17 如何证明答辩基于真实项目

答：创建会话时必须提供作业提交或代码审查编号。后端按用户和租户校验记录，再加载作业要求、自动分、薄弱点和问题列表。模型生成问题时使用这些结构化上下文，而不是只有一个通用答辩提示词。

## 17.18 为什么接口先返回任务编号

答：代码运行和模型评审可能需要数秒甚至更久。立即返回 202 和任务编号可以避免请求超时，前端轮询状态并展示进度。生产环境应把任务放进持久化队列，避免 Web 进程重启导致任务丢失。

## 17.19 数据如何防止越权

答：JWT 证明用户身份和角色，业务查询还必须带租户编号和数据所有者条件。学生访问提交时会比较记录中的 student id，教师写操作会检查 teacher 或 admin 角色。认证和数据归属校验缺一不可。

## 17.20 大模型密钥失效怎么办

答：模型调用失败不应该让课程数据和代码测试一起失效。代码审查降级到本地规则，作业评测继续运行沙箱，答辩使用固定问题并把得分标记为待评价。QA 的自然语言生成会受到影响，因此界面和日志要明确服务状态。

## 17.21 如何评估这个系统

答：需要分别建立路由、RAG、代码评分和答辩四类评测集。RAG 可以看召回率、重排后相关性和答案有据率；代码评分可以对比教师标准分和问题标注；答辩可以评价问题相关性和报告一致性。每次修改模型或提示词都应该离线回归，而不是只看几个演示样例。

## 17.22 如果并发量增加怎么办

答：先把代码执行和模型任务从 FastAPI 进程迁移到队列 Worker；沙箱执行节点按任务量水平扩容；本地模型可以独立成推理服务；数据库和 Milvus增加连接池、索引和监控；再对不同任务设置限流、超时和优先级。

## 17.23 项目最大的不足是什么

答：当前最大的工程边界是后台任务和沙箱仍面向本地原型，没有持久化队列和独立执行集群；最大的算法边界是缺少教师标注评测集，不能用演示分数证明评价准确率。下一步应优先补这两项，而不是继续增加 Agent 数量。

## 17.24 如果重新设计会改什么

答：我会先定义事件和状态模型，把提交、测试、审查、确认和答辩做成可恢复任务；然后拆出独立沙箱 Worker，使用 Postgres Checkpointer 保存 Agent 进度；最后建立评测集和可观测平台，持续比较不同模型、提示词和检索参数。

## 17.25 这个项目和普通管理系统有什么区别

答：普通管理系统主要完成数据增删改查；这个项目在数据流中加入了检索、模型判断、代码执行、状态机和人工确认。业务记录不只是被保存，还会成为后续 Agent 的上下文和决策依据。

## 17.26 你的项目数据从哪里来

答：要按类型回答，不能笼统说“来自数据库”。课程知识来自教师确认的 PDF、Word 或 Markdown，作业要求和测试标准来自教师配置，源代码和答辩回答来自登录学生，运行结果来自 Docker 对具体测试用例的实际执行，模型只根据这些上下文生成评价建议，最终成绩由教师确认。当前仓库中的示例课程和 3 个用例由初始化脚本生成，属于演示数据，不是学校生产数据。

## 17.27 如何保证数据真实性

答：我没有声称系统能绝对保证真实性，而是建立可追溯和可复核机制。知识块记录文档来源和位置，学生文件绑定用户、作业、提交时间和 SHA-256，测试结果绑定提交与用例并保存退出码和耗时，答辩必须关联真实提交，正式成绩记录审核教师和时间。另外，模型结果与原始数据分开保存，低置信度问答走兜底，无密钥时不伪造模型分数。当前还缺文档审批版本、不可篡改审计、代码查重和教师标注评测集，这是后续需要补齐的部分。

# 18 项目演示讲解顺序

面试演示不要从登录页开始逐个菜单点。建议用一条业务主线展示，控制在 5 到 8 分钟。

## 第一步 教师配置

使用教师账号进入课程作业配置，展示课程、作业要求和三个测试用例。先主动说明这是一组初始化脚本生成的演示数据，再解释真实使用时课程规则和测试标准由教师创建。公开用例帮助学生调试，隐藏用例用于检查边界和减少硬编码。

## 第二步 学生提交

切换学生账号选择“成绩统计器”，上传示例 Python 文件。说明接口立即返回提交编号，后台并行运行沙箱测试和质量分析。

## 第三步 查看评测

打开提交结果，依次指出提交编号、功能分、质量分、具体测试用例、运行结果、问题列表和待确认状态。强调总分可以向前追溯到学生文件、教师标准和容器执行证据，不要只报一个孤立分数。

## 第四步 教师确认

切回教师端打开待确认队列，说明自动结果是辅助证据，教师可以修改成绩并填写评语，发布后学生才看到最终分数。

## 第五步 代码审查

上传一份包含 eval、裸 except 或可变默认参数的代码，展示本地规则即使没有密钥也能定位问题。说明配置密钥后会增加六维并行语义评审。

## 第六步 项目答辩

选择刚才的提交创建答辩。回答一到两轮后指出当前阶段和轮次，再输入结束答辩。说明无密钥模式不会伪造评分；有密钥时会生成结构化报告。

## 第七步 补充 RAG

如果面试官对 Agent 或 RAG 感兴趣，再展示课程问答，点开来源并回到原文核对，同时解释混合召回、重排和置信度路由。要说明“有引用”表示可追溯，不代表所有生成内容天然正确。时间紧张时不必把每个页面都展示一遍。

# 20 学习与背诵建议

## 20.1 第一层 先会讲业务

不看文档，能够回答：

- 谁使用这个系统。
- 教师和学生各自完成什么操作。
- 一份代码从上传到发布成绩经历哪些步骤。
- 为什么最终成绩需要教师确认。
- 每类关键数据由谁提供，怎样从最终成绩追溯到原始提交和测试标准。

## 20.2 第二层 再会讲四个 Agent

每个 Agent 只记住三个词：

| Agent | 三个关键词 |
|---|---|
| 程序设计问答 | 混合检索 精排 记忆 |
| 编程作业评测 | 沙箱 并行 教师确认 |
| 代码质量审查 | AST 六维 降级 |
| 项目答辩 | 真实上下文 状态机 报告 |

## 20.3 第三层 会讲三个难点

建议重点准备：

1. 为什么不能直接运行学生代码，Docker 限制了什么，生产环境还缺什么。
2. 为什么不能让大模型直接发布分数，功能测试、质量分析和教师确认如何配合。
3. 数据分别来自教师、学生、系统还是模型，如何保证来源可追溯且不把演示数据说成真实业务数据。

这两个问题既能体现 Agent 理解，也能体现安全和工程意识。

## 20.4 第四层 准备边界

主动记住三个未完成项：

- 后台任务还没有持久化队列。
- Docker 还是本地原型沙箱。
- 还没有教师标注的完整评测集。

知道边界并能说明改进方案，比声称项目已经“完全生产可用”更专业。

## 20.5 最终自测

面试前尝试脱稿回答以下问题：

1. 用 30 秒介绍项目。
2. 用 2 分钟讲完整业务链路。
3. 解释为什么需要四个 Agent。
4. 解释一次作业如何得到最终成绩。
5. 解释 Docker 沙箱的安全限制。
6. 解释 RAG 为什么需要混合检索和重排。
7. 说明一个自己真正解决的难点。
8. 说明当前项目最大的不足和下一步计划。
9. 说明课程知识、测试用例、学生代码、运行结果和最终成绩各自来自哪里。
10. 解释 SHA-256 能证明什么、不能证明什么，以及为什么还需要教师终审。

如果这些问题能自然回答，并且可以继续解释其中的技术原因，就已经具备把项目讲给面试官的基础。

# 结语

CodeMentor Agent 的重点不是把多个模型接口放在一起，而是把有来源的课程和作业数据、可复核的确定性测试、语言模型判断、业务状态和教师责任连接成一条可解释的课程实训流程。

面试时应始终围绕五件事展开：项目解决什么问题、数据从哪里来、为什么采用当前架构、关键流程如何保证可控、当前边界准备怎样改进。只要能够把这五件事讲清楚，就不需要死记代码，也能证明自己真正理解了项目。
